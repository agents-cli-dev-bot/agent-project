# Agent spec

## Overview

A customer support agent that answers product questions, troubleshoots common issues, and escalates complex cases to human agents. It uses three tools: product lookup, known-issue matching, and human escalation. For questions outside its scope, it politely refuses. After deployment, a self-evaluation feedback loop identifies weak responses and drafts new eval cases.

## Language and framework

ADK Python (`google-adk`), scaffolded with the `adk_python` template and `agent_runtime` deployment target.

## Example use cases

1. **Product lookup**: "What are the specs for product P-1001?" → agent calls `lookup_product_info("P-1001")` and returns the product details.
2. **Known issue**: "I'm getting error code ERR-500." → agent calls `check_known_issues("ERR-500")` and returns the known fix or status.
3. **Escalation**: "My enterprise deployment has been down for 6 hours and I'm losing revenue." → agent calls `escalate_to_human` with priority `critical` and a case summary.
4. **Out-of-scope refusal**: "What's the weather today?" → agent politely declines, stating it only handles product support.
5. **Polite tone**: Any response should be professional, empathetic, and clear.

## Tools

### `lookup_product_info(product_id: str) -> dict`
- **Purpose**: Returns product name, description, specifications, and pricing for a given product ID.
- **Auth**: None (simulated local data).
- **Returns on unknown ID**: `{"error": "Product not found", "product_id": product_id}`
- **Returns on empty input**: `{"error": "product_id is required"}`

### `check_known_issues(error_code: str) -> dict`
- **Purpose**: Returns known issue description, status, and recommended resolution steps for a given error code.
- **Auth**: None (simulated local data).
- **Returns on unknown code**: `{"error": "No known issue found", "error_code": error_code}`
- **Returns on empty input**: `{"error": "error_code is required"}`

### `escalate_to_human(case_summary: str, priority: str) -> dict`
- **Purpose**: Creates a support ticket and routes to a human agent.
- **Priority levels**: `low`, `medium`, `high`, `critical`
- **Auth**: None (simulated).
- **Returns**: `{"ticket_id": "<generated>", "priority": priority, "status": "escalated", "message": "A human agent will contact you..."}`
- **Returns on invalid priority**: `{"error": "Invalid priority. Must be one of: low, medium, high, critical"}`

## Constraints and safety rules

- **Scope enforcement**: The agent must refuse questions unrelated to product support (e.g., general knowledge, weather, personal advice). Enforced in the system instruction.
- **Escalation threshold**: Cases involving revenue loss, production outages, data loss, security incidents, or repeated failed troubleshooting should be escalated at `high` or `critical` priority. Enforced in the system instruction.
- **Priority validation**: `escalate_to_human` validates that priority is one of the four allowed values; returns an error dict otherwise.
- **No hallucination of product data**: The agent must only report product information returned by `lookup_product_info`, not invent specs.

## Success criteria

Eval bar: all 5 eval cases pass with score ≥ 4/5 on a 1–5 LLM-judge rubric.

| # | Case | Pass condition |
|---|---|---|
| 1 | Product lookup | Calls `lookup_product_info` and includes returned data in reply |
| 2 | Known issue matching | Calls `check_known_issues` and surfaces the fix/status |
| 3 | Appropriate escalation | Calls `escalate_to_human` with correct priority and confirms ticket |
| 4 | Out-of-scope refusal | Declines without tool calls; mentions it only handles product support |
| 5 | Response tone | Reply is polite, empathetic, professional; no robotic or harsh language |

## Reference recipes

No core recipes are ported directly. The self-evaluation feedback loop is implemented as a lightweight post-turn tool (`draft_eval_case`) rather than the full `ambient-quality-agent` extension, keeping scope manageable for this project size.

## Deployment

- **Target**: Agent Runtime (`agent_runtime`)
- **Projects**: dev → stg → prd (three separate GCP projects)
- **CI/CD runner**: Cloud Build (`google_cloud_build`)
- **Promotion flow**: dev → stg → prd via CI/CD pipeline

## Assumptions

- Product and known-issue data are simulated in-memory dictionaries (no external DB).
- Model: `gemini-2.0-flash` on Vertex AI (env vars `GOOGLE_GENAI_USE_VERTEXAI`, `GOOGLE_CLOUD_PROJECT`, `GOOGLE_CLOUD_LOCATION` are set).
- Agent name: `customer_support_agent` (valid Python identifier).
- Self-evaluation loop implemented as a `draft_eval_case` tool the agent can call internally, not the full AQuA extension.
- GCP project IDs for dev/stg/prd are taken from environment at deploy time (not hardcoded here).
- GitHub PAT and app installation ID provided via `$GH_TOKEN` and `$GITHUB_APP_INSTALLATION_ID`.
- Eval bar: ≥ 4 out of 5 cases pass before promoting to deploy.
